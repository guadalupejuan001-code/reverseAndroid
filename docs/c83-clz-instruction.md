# C83 — CLZ vector que bloqueó el Android real

C82 terminó su cuarta etapa con salida nativa2, sin watchdog ni señal, en85.047.727.997 instrucciones. El error observado fue `Unsupported AArch64 instruction 0x6ea04800 at 0x7283e70a78`. La última frontera limpia sigue siendo C82 etapa3:85.000.000.000, SHA-256 `73bdb15f90ce9b03efff6794c38e11f561f102246cd31ab21ae25ae54ffea85c`. Se recuperaron sus cuatro ZIP y piezas, el snapshot íntegro y la admisión original. El candidato fallido nunca se admite ni se usa como fuente.

El opcode es `CLZ V0.4S,V0.4S`. Arm DDI0602, marzo2025, CLZ (vector), página1136, especifica el número de ceros consecutivos desde el bit más significativo de cada elemento. Están asignadas seis formas:8B,16B,4H,8H,2S,4S. El valor cero produce el ancho del elemento; no cambia FPSR, FPCR ni NZCV. Se comprueba acceso FP/SIMD; las formas de64 bits por elemento y las escalares no se aceptan. [Fuente primaria de Arm](https://documentation-service.arm.com/static/67e40f3398aa3c3b6eea6a85).

Los870 archivos importados permanecen idénticos. `prepare-clz-extension.py` verifica toda la referencia, copia `src` a un directorio nuevo e inserta una inclusión en el decodificador de esa copia. La implementación está en `extensions/aarch64-clz.inc`. El manifiesto identifica los hashes de ambos decodificadores y de la extensión. El nuevo ejecutable se llama `epoch-clz`; no se presenta como el binario original72f. XI/Ether, RAM lógica, reloj, semilla, cadencia64, disco, formato RVG y observadores y criterios de arranque se conservan.

La suite reproduce primero el rechazo exacto en el motor de referencia. La candidata pasa30.887 casos y1.112.149 comprobaciones en Release y UBSan: seis formas, todos los pares de registros, alias, todos los valoresB/H, ceros, cada posición del primer bitS, parte superior del destino, FPCR/FPSR/NZCV, registros enteros, memoria y núcleo XI/Ether, restauración, trampas FP y rechazo sin cambios de formas reservadas.
