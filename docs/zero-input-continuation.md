# Continuing an admitted boundary with zero new input

The reusable continuation scripts retain the entire original snapshot, input
ledger and console history across a new bounded campaign. They are prepared for
the next fully admitted source if the active C88 budget ends before actual boot.
No follow-up source plan has been selected or executed by these files yet.

`prepare-zero-input-continuation-state.py PLAN SOURCE REPORTS` requires the full
original epoch preflight, whole RVG digest, authenticated source campaign proof,
original epoch and kernel, enforcing policy, identical completed input history,
the real earlier priority reply and the unchanged957f22e2 native binary. It
authenticates the complete console prefix and copies it only as observation
history. A temporary peripheral restart may be retained as a valid source; fresh
live peripheral verification remains mandatory for completion.

`run-zero-input-continuation-stage.py PLAN STAGE` supplies a literal `-` input
argument on every native run. Configuration cannot request a new UART file, and
the original epoch mechanism rejects an unrequested native UART event. Every
stage keeps the complete original admission, snapshot roundtrip, report/process
binding, kernel and property observations, console bytes and all prior events.
There are at most16 stages of at most1B instructions each, with the original
900000ms host cap and unchanged logical2GiB RAM, disk, codecs, seed, cadence and
IRQ. Complete transport preservation is required before another stage or older
duplicate removal.

The scripts can also take a booted source through a short zero-input display
settling stage. Their completion means genuine original BOOT1, live SystemServer
and fresh peripherals. Actual usable UI and a meaningful real gesture response
still require the separate authenticated UI test and actual frame review.
